# Bootloader UEFI : corrections de l'ordre 5

Branche : `fix/UEFI-bootloader`. Base de ce lot : `c5c6d57`.
Périmètre : R15 à R19 de la [revue initiale](C:/src/strat9-os/doc/BOOTLOADER_REVIEW_2026-09-12.md).
Cibles : PC x86-64 UEFI et QEMU/OVMF. L'architecture du bootloader est conservée.

| Constat | Correction implémentée |
| --- | --- |
| R15 | La sélection GOP filtre les formats et la géométrie avant de comparer les résolutions. Après chaque tentative de `SetMode`, le mode courant est validé avec la taille réelle de son framebuffer. Un échec permet de conserver un mode courant compatible ou d'essayer les suivants. L'absence de mode utilisable laisse une configuration vidéo nulle et un diagnostic sur la console firmware. |
| R16 | Les octets RGB et BGR correspondent désormais aux décalages transmis au noyau. `BltOnly` et `Bitmask` sont explicitement exclus ; aucun format n'est inventé. Le pas en pixels est converti en octets avec contrôle des limites. |
| R17 | Les fenêtres framebuffer et environnement utilisent toutes les entrées PTE successives. Le changement de PT après 512 pages est continu. L'arrondi physique conserve le décalage initial ; `fb.virt` comprend ce décalage. Le budget exact des tables est calculé avant l'allocation et vérifié après construction. |
| R18 | Les droits proviennent des `p_flags` ELF : code RX, constantes R/NX, données et BSS RW/NX. Les alias identité et HHDM du code et des constantes sont R/NX ; les autres pages de RAM sont RW/NX. Les segments W+X et les segments de droits différents partageant une page sont refusés. Le script de liaison rend les droits des quatre segments explicites. |
| R19 | Suppression de la réécriture de PAT[4]. PAT[0] doit déjà être WB et PAT[3] UC. Le framebuffer est UC sur ses trois alias, dont le HHDM effectivement utilisé par le noyau. RAM identifiée : WB ; trous et MMIO : UC. Le passage CR3 draine les caches avec le cache désactivé et invalide les traductions héritées. |

La sélection accepte exclusivement les formats standard à 32 bits, avec largeur et hauteur non nulles, pas au moins égal à la largeur, taille visible contenue dans `FrameBufferSize`, adresse non nulle et alignée sur quatre octets. Un framebuffer peut commencer au milieu d'une page. L'aperture complète annoncée par GOP, arrondie aux pages, est limitée à 1 Gio pour sa fenêtre dédiée. Une configuration dépassant cette limite est exclue de la sélection. Ces règles s'appuient sur le contrat GOP et sur l'accès aux pixels par `u32` du noyau ; l'ordre des octets est défini dans la [spécification UEFI, Graphics Output Protocol](https://uefi.org/specs/UEFI/2.10/12_Protocols_Console_Support.html).

L'aperture est aussi ajoutée aux réservations de la carte transmise, sans transfert de propriété au gestionnaire `FreePages`. Cela protège le cas où le framebuffer est situé dans une région de RAM autrement réutilisable. Un recouvrement avec les allocations permanentes ou l'image EFI provoque un échec. Les données de géométrie pures sont dans [graphics.rs](C:/src/strat9-os/workspace/bootloader/src/graphics.rs) ; la sélection firmware et les réservations restent dans [main.rs](C:/src/strat9-os/workspace/bootloader/src/main.rs).

Le [constructeur de tables](C:/src/strat9-os/workspace/bootloader/src/page_tables.rs) travaille sur une tranche bornée de mots, ce qui permet de parcourir les tables réellement produites dans des tests hôtes. Seule l'enveloppe utilisant l'arène physique nécessite un accès mémoire `unsafe`. Les feuilles de 2 Mio restent utilisées lorsque les droits et sélecteurs de cache du plan sont uniformes. Les intersections avec le noyau, les frontières de cache, l'image EFI dans l'alias identité et les deux premiers Mio sont découpées en pages de 4 Kio. Les fenêtres virtuelles et la limite HHDM de 512 Gio sont conservées ; aucune feuille de 1 Gio n'est introduite.

La liste des plages WB est construite à partir des types de RAM UEFI et de `MemoryAttribute::WRITE_BACK`, triée et fusionnée avant la création des tables. La carte finale peut redécouper ces plages à la suite des allocations, mais ne peut pas modifier leur classification sans provoquer un arrêt. La RAM allouable doit annoncer la capacité WB. Les attributs de cache des tables et de leurs alias restent WB. Le noyau conserve les mappings existants ; ses nouveaux mappings de RAM sont NX/WB, ceux de MMIO NX/UC.

PAT et MTRR ne sont pas reprogrammés. Les MTRR restent ceux du firmware ; WB désigne ici le sélecteur PAT demandé pour la RAM, dont le type effectif reste soumis aux MTRR. Le choix UC pour la vidéo privilégie une politique cohérente et peut réduire les performances graphiques. Une optimisation WC devra gérer la cohérence des alias et des processeurs. Intel documente les sélecteurs PAT, les précautions de cache/TLB et la conservation de PAT après INIT dans le [manuel système, volume 3A, sections 13.12.3 et 13.12.4](https://cdrdv2-public.intel.com/835754/253668-sdm-vol-3a.pdf).

Le noyau reçoit le marqueur `loader.paging=wx-uc-v1`, sans changement du format binaire de l'ABI. Lorsqu'il reconnaît ce contrat, il retire l'exécution des pages identité de l'image EFI avant les allocations physiques. L'image avait besoin de cet accès RX uniquement pour terminer la transition CR3. Le marqueur évite d'appliquer cette opération aux tables d'un ancien loader ou d'un autre chemin de démarrage.

Le [trampoline SMP](C:/src/strat9-os/workspace/kernel/src/arch/x86_64/smp.rs) reçoit une adaptation indispensable à NX : sa page identité à `0x8000` devient RX avant SIPI, tandis que le BSP écrit le code et les paramètres via son alias HHDM RW/NX. Les bits « accessed » de sa GDT sont prépositionnés. Chaque AP vérifie PAT[0]/PAT[3] avant d'activer la pagination ; un désaccord produit `P` sur E9 et arrête cet AP. Les destinations des sauts lointains sont calculées à partir des labels pour rester correctes lorsque le stub s'allonge.

Après l'arrivée de tous les AP attendus, le BSP retire l'exécution de cette page ; chaque processeur invalide sa traduction à la barrière de démarrage. Si un AP dépasse le délai existant, la page reste temporairement exécutable pour ne pas faire tomber un processeur encore dans le trampoline. Cette exception physique W+X, limitée à la préparation et au démarrage SMP, ne concerne pas le texte du noyau. Le comportement existant de poursuite après timeout SMP est conservé.

Douze nouveaux tests Rust sont préparés, sans exécution : neuf dans [boot_graphics.rs](C:/src/strat9-os/workspace/kernel-l2-tests/tests/boot_graphics.rs), deux cas ELF dans [boot_memory.rs](C:/src/strat9-os/workspace/kernel-l2-tests/tests/boot_memory.rs), un cas PAT dans [boot_transition.rs](C:/src/strat9-os/workspace/kernel-l2-tests/tests/boot_transition.rs). Ils couvrent les octets des couleurs, la géométrie invalide, les petites apertures, les décalages physiques, les frontières entre PT, les droits des alias, le cache d'un framebuffer dans la RAM, les pages de garde de l'arène, les limites et les changements de classification firmware. Le test du budget maximal existant est adapté : 2 568 pages pour son scénario de 512 Gio de couverture et un noyau de 1 Gio aligné sur 2 Mio.
